# Visitor Pass — List Approvers Panel (Part B) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show, on the Open Transaction detail page for a Visitor Pass transaction, the list of configured approvers (from `MatrixTypeApprover`) that scope-match the transaction's Matrix Type + Department + Business Unit + Location.

**Architecture:** `Transaction` gains two new nullable FK columns (`businessUnitId`, `locationId`) alongside the existing `departmentId`, so a transaction can carry a real, scoped identity to match against `MatrixTypeApprover` rows. The Visitor Pass creation form swaps its free-text Location field for a dropdown and gains a new required Business Unit dropdown, both sourced from the real `BusinessUnit`/`Location` tables. The transaction detail page server-queries `MatrixTypeApprover` filtered by the transaction's own four FKs (matrix type + department + business unit + location) and renders the result in a new panel below the line items table, grouped by approval level.

**Tech Stack:** Next.js (App Router, Server Components), Prisma + PostgreSQL, Zod, Vitest + Testing Library.

## Global Constraints

- Scope is **Visitor Pass only** — no changes to Halfday/Undertime/Others/Out for Lunch/Routing to other Business Unit.
- The existing free-text `Transaction.visitLocation` column is **kept, not dropped** (historical display for pre-existing rows) — but new Visitor Pass transactions must stop writing to it; the create form and API no longer send/persist it.
- No per-approver live approval status, no Post/Delete-transaction button changes, no backfill of `businessUnitId`/`locationId` onto existing transactions — out of scope.
- All new required-field validation (Business Unit, Location) must route through the existing `lib/transactionFieldSets.ts` `getActiveFields`/`findMissingRequiredField` pattern — no new/duplicate validation mechanism.
- **This plan includes a schema migration against a live database** (local PostgreSQL `perso_proj`, per the branch's current dev setup — see `docs/superpowers/2026-07-19-green-rebrand-handoff.md` §3ai/§4). Expect the harness's safety classifier to flag the `npx prisma migrate dev` step on first dispatch as a destructive/hard-to-reverse action — this is expected on this branch (not a bug); get the user's go-ahead before proceeding if it's blocked, per standing branch precedent.
- After any migration that runs while a dev server is up, **restart the dev server** (`Get-Process -Name node | Stop-Process -Force` then `npm run dev`) — a long-running Next.js dev server keeps a stale in-memory Prisma Client and will throw on the new columns otherwise (documented gotcha, handoff §5).
- Test command: `npx vitest run <path>` for a single file, `npm test` for the full suite. API route tests use `// @vitest-environment node` at the top of the file (already present in the files this plan touches) and hit the real local dev database — a known ~1-2 test baseline failure in `prisma/seed.test.ts` (seed-admin credential drift, reference-data drift) is expected and unrelated to this plan; don't try to fix it.
