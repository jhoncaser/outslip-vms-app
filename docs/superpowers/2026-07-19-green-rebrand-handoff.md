## 3b. Follow-up work: logout redirect — DONE

User asked that logging out redirect back to `/login` instead of leaving the session on whatever page triggered it. Traced the gap: `components/dashboard/Sidebar.tsx`'s Logout button is a native `<form action="/api/auth/logout" method="post">`; the route handler (`app/api/auth/logout/route.ts`) was returning a plain `NextResponse.json({ success: true })` with no redirect. `proxy.ts`'s auth-redirect middleware doesn't cover this either — its `config.matcher` explicitly excludes `/api/*` — so the fix has to live in the route handler itself.

Implemented directly (small, mechanical, unambiguous — no brainstorm/plan needed): `route.ts` now returns `NextResponse.redirect(new URL("/login", request.url), 303)` (explicit 303 for correct POST-Redirect-GET semantics on a native form POST) with the session cookie cleared on the redirect response. `route.test.ts` updated to assert `303` + `location: http://localhost/login` + cleared cookie. Verified: isolated test passes, full suite 68/68, and live-verified against the running dev server via direct HTTP request (`POST /api/auth/logout` → `303 See Other`, `location: http://localhost:3000/login`, cookie cleared) — no dev-server restart needed, Next.js hot-reloads route handler changes. User tested in-browser and confirmed it works.

Commit `41c9098`: "Redirect to /login on logout". Pushed to `origin/green-rebrand`.

## 3f. Bugfix: change-password validation messages — DONE

Two related fixes to `lib/validation/auth.ts` and `app/api/auth/change-password/route.ts`:

1. **Specific messages instead of generic "Invalid request":** the route now surfaces the actual Zod issue message (`parsed.error.issues[0]?.message`) — "Password must be at least 8 characters" or "Passwords do not match" — instead of a blanket "Invalid request" for any validation failure. Confirmed safe to be this specific here (unlike login) since there's no account-enumeration risk once a user is already authenticated and changing their own password.
2. **Real bug found and fixed:** `confirmPassword` had its own independent `.min(8, ...)` check in the schema, which ran *before* the `.refine()` cross-field match check. So whenever `confirmPassword` was short — even when the actual problem was a mismatch with `newPassword` — the user saw "Password must be at least 8 characters" instead of "Passwords do not match" (user caught this from a screenshot: `newPassword="admin"`, `confirmPassword="adminadmin"`, both short-and-mismatched, message didn't address the mismatch). Fixed by dropping the redundant length rule on `confirmPassword` — its only real job is matching `newPassword`, which already enforces the length floor. Added a regression test (`route.test.ts`: "returns 'Passwords do not match' when confirm is short and mismatched, not a length error") covering exactly this case.

Commit `17e6475`: "Show specific validation messages on change-password errors".

## 5. Known environment gotchas

- Neon cold-start: `P1001`/connection errors on DB-backed tests or `prisma migrate deploy` — retry once before concluding anything is broken (per the plan's Global Constraints).
- Seed-admin "drift" is no longer drift (see §3l): `prisma/seed.test.ts` failing 1/N is the expected baseline once the user has set their own real password — do not reset the seed admin's password/`mustChangePassword` without the user asking. **Caveat (see §3q):** this baseline can silently flip back to 0 failures if a seed-related code change's own test runs re-trigger a credential reset against the live DB (this happened once already, Task 1 of the settings-setup-tables plan). If `seed.test.ts` unexpectedly passes clean, don't assume the baseline changed for a good reason — check whether the admin's real credentials just got clobbered again, and tell the user immediately if so.
- `npm install` is restricted to `npm install --ignore-scripts`; no new deps are expected in this plan.
- Two other worktrees exist in this repo (`.claude/worktrees/homepage` on branch `worktree-homepage`, `.claude/worktrees/registration-login` on branch `worktree-registration-login`) sitting on older pre-rebrand commits. They predate this plan and are unrelated to it — don't confuse their state with `green-rebrand`'s.
- **Stale Prisma Client in a long-running dev server (found §3r):** if a `prisma migrate dev`/`migrate deploy` runs while a dev server is already up, that server keeps its in-memory Prisma Client from before the migration and throws `Cannot read properties of undefined (reading 'findMany'/etc.)` on any newly-added model — Next.js dev/Turbopack does not hot-reload a regenerated Prisma Client into a running process. Kill and restart the dev server after any mid-session migration, even though the regenerated client is already correct on disk.
- **Parallel-test-worker races against the shared live DB (found §3r):** vitest runs test files in parallel workers by default; two files that both create/read rows in the same table (e.g. `matrix-types/route.test.ts`'s `"Route-Test *"` fixtures vs. `seed.test.ts`'s exact-array assertions) can transiently pollute each other if one file's cleanup hasn't finished when the other's assertion runs. If a full-suite run shows more/different failures than the known seed-admin baseline, re-run the specific files together before concluding there's a real regression.
- **`"Route-Test"`-prefixed fixture names can collide across files, not just transiently pollute (found §3t):** `matrix-types/route.test.ts`'s cleanup uses `deleteMany({ where: { name: { startsWith: "Route-Test" } } })` — broad enough to delete ANY other file's fixture that happens to start with the same prefix (this deleted `transactions/route.test.ts`'s `"Route-Test Matrix Type"` fixture mid-run, causing real FK-violation test failures, not just cosmetic pollution). Fixed by renaming the colliding fixture; going forward, give each test file's fixtures a distinct prefix rather than reusing `"Route-Test"` project-wide.
- **`npm run build` corrupts a concurrently-cached `next dev` session (found §3y):** running `npm run build` (e.g. as a task's verification step) writes production manifests into `.next/`, the same directory `next dev`/Turbopack uses for its own dev-mode cache and routing manifests. If a dev server was already running, or gets started afterward without clearing `.next` first, routes inside route groups (e.g. everything under `app/(authenticated)/`) started 404ing or 500ing with a Turbopack `TurbopackInternalError: Failed to restore task data (corrupted database or bug)` referencing a missing `.sst` cache file — while routes outside any group (e.g. `/login`) kept working, which is the tell. Compounding factor: on Windows, `pkill -f "next dev"` (via Git Bash) did not reliably kill the actual `node.exe` process holding the port/cache locks, so repeated "kill and restart" attempts left multiple orphaned node processes contending for the same single-writer Turbopack cache (`Persisting failed: Another write batch or compaction is already active`). **Fix that actually worked:** `Get-Process -Name node | Stop-Process -Force` (PowerShell, kills all node processes — safe here since this checkout doesn't run any other persistent node service) → `rm -rf .next` → one fresh `npm run dev`. Going forward: after any task step that runs `npm run build`, either clear `.next` before the next `npm run dev`, or just don't run `npm run build` and `npm run dev` against the same `.next` directory in the same session without a clean in between.
